Module 00 — Introduction

What is Web Hosting?

Before we deploy anything, let's understand exactly what hosting is, how it works, and the different types of hosting you can use — for free.

8 min read
Beginner
1 quiz

What Does "Web Hosting" Actually Mean?

Imagine you build a house. Building it is one thing — but you also need land to put it on so people can find it. Web hosting is that land.

When you create a website (HTML, CSS, JavaScript files), those files live on your computer. But only your computer can see them. To make the world see them, you need to put them on a server — a computer that's always on and connected to the internet. That's hosting.

Simple definition

Web hosting = renting space on a server where your website files live, so anyone on the internet can access them 24/7.

How the Web Works — The Big Picture

Before we go deeper, let's understand what happens when someone visits your website:

You → DNS → Server → Website (in milliseconds)

Step by step:

  1. You open a browser and type mysite.com
  2. DNS translates that name into an IP address (like a phone book for the internet)
  3. The browser sends a request to the server at that IP address
  4. The server finds your website files and sends them back
  5. Your browser renders them into the page you see

Common Misconceptions

❌ "Hosting is expensive"

Wrong. GitHub Pages, Netlify, Vercel, Render, Cloudflare Pages — all offer permanent free tiers.

❌ "Free hosting has ads"

Old-school free hosting had ads. Modern platforms (GitHub, Netlify, Vercel) have zero ads.

❌ "I need to know Linux"

Nope. Modern platforms are deploy by push — you push code, it's live.

❌ "Free = slow"

Free hosting on CDNs is often faster than paid shared hosting.

Summary

  • Web hosting = putting your files on an always-online server
  • DNS turns a domain name into a server address
  • Static hosting is free forever on modern platforms
  • You don't need Linux or server knowledge anymore
  • Free is fast and ad-free on modern platforms

What is GitHub Pages?

GitHub Pages is a free static site hosting service built into GitHub. Every repository can become a website.

What you get for free

⚠️ Important Note for Tanzania Users

Render may be slow or unreachable on some networks

Users on Halotel Tanzania (and a few other regional ISPs) have reported that onrender.com sites sometimes fail to load or take 50+ seconds.

This is not a Render problem — it's a network routing issue between some Tanzanian ISPs and Cloudflare/AWS.

What you can do:

  • ✅ Use a VPN — bypasses the issue 90% of the time
  • ✅ Try mobile data — Vodacom, Airtel, Tigo usually work
  • ✅ Deploy on Netlify/Vercel — better local reliability
  • ✅ Add Cloudflare proxy — put Cloudflare in front of Render

Bottom line: Render works great, but test on Halotel before committing if your audience is in Tanzania.

Module 06 — HTTPS & Security

HTTPS & Security

HTTPS inalinda data yako kwa encrypt ya SSL/TLS. Modern hosts wanatoa bure — lakini lazima ujue kinachoendelea nyuma.

12 min
Intermediate
2 quizzes

Why HTTPS?

  • 🔒 Encryption — data in transit is scrambled
  • 🛡️ Authentication — proves the site is real
  • 📊 SEO — Google ranks HTTPS higher
  • ⚠️ Browser warnings — HTTP sites show "Not Secure"
  • 🚀 HTTP/2 — requires HTTPS
HTTPS wraps your data in an encrypted tunnel

How HTTPS Works (Simplified)

  1. Certificate Authority (Let's Encrypt, DigiCert) issues a certificate proving your domain is real
  2. When a user visits your site, browser checks the certificate
  3. If valid, browser and server exchange encryption keys
  4. All data is now encrypted end-to-end

Free SSL from Let's Encrypt

Let's Encrypt is a free, automated Certificate Authority. All modern hosts integrate it:

ProviderHTTPS setup
GitHub PagesAutomatic, no config
NetlifyAutomatic with Let's Encrypt
VercelAutomatic
RenderAutomatic
Cloudflare PagesAutomatic
You get HTTPS free, automatically

When you add a custom domain to any modern host, HTTPS is provisioned for you in minutes. You don't need to do anything.

Force HTTPS

Make sure all traffic uses HTTPS. Modern hosts do this by default. On GitHub Pages:

  1. Settings → Pages
  2. Check Enforce HTTPS

Security Headers (Bonus)

Add these headers for extra security. On Netlify, create a file called _headers:

/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: geolocation=(), microphone=()

Common HTTPS Mistakes

❌ Mixed content

Loading HTTP resources (images, scripts) on an HTTPS page. Browsers block these.

Fix: Change all http:// to https:// in your code.

❌ No HTTPS on custom domain

If HTTPS doesn't auto-provision, wait 24 hrs, then check DNS. Or contact host support.

❌ Expired certificate

Rare with Let's Encrypt (auto-renews every 90 days), but possible if auto-renew fails.

Module 07 — CI/CD Pipelines

CI/CD with GitHub Actions

Automate deployments, tests, and builds. Every push → automatically deploy. No manual steps.

13 min
Advanced
1 quiz

What is CI/CD?

  • CI (Continuous Integration) — auto-run tests on every push
  • CD (Continuous Deployment) — auto-deploy when tests pass

Modern hosts (Netlify, Vercel, Render) already do CD for you. But GitHub Actions gives you full control — custom builds, tests, notifications, deployments.

GitHub Actions Basics

Workflows live in .github/workflows/ in your repo. Each is a YAML file:

# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run build

Common Workflows

1. Auto-deploy to GitHub Pages

name: Deploy to Pages
on:
  push:
    branches: [ main ]

permissions:
  contents: read
  pages: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v4
      - uses: actions/upload-pages-artifact@v3
        with:
          path: '.'
      - uses: actions/deploy-pages@v4

2. Run tests on every PR

name: Tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test

3. Keep Render app awake

name: Keep Alive
on:
  schedule:
    - cron: '*/14 * * * *'

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - run: curl -s https://your-app.onrender.com

4. Auto-deploy to a VPS (SSH)

name: Deploy to VPS
on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: SSH Deploy
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: cd /var/www && git pull && systemctl restart app

Using Secrets

Never hardcode API keys or SSH keys in workflows. Use GitHub Secrets:

  1. Repo → Settings → Secrets and variables → Actions
  2. Add new secret (e.g. VPS_HOST, API_KEY)
  3. Access in workflow via ${{ secrets.SECRET_NAME }}
